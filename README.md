# Old Miyu data migration (miyu-migrate)

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

This repository is a package for the new Miyu. It migrates the data folder of the old Miyu (0.7.x) into the new Miyu. Once you install the package, Miyu gains one more command, `miyu migrate`.

Before you migrate, stop the old version and move the old folder aside, then install the package and run the migration:

```
mv ~/.miyu ~/.miyu-0.7        # Stop the old version first, then move the old folder aside: while the old folder occupies ~/.miyu, the new core cannot start
miyu pkg install migrate
miyu migrate ~/.miyu-0.7
```

The detailed steps, what is migrated, what is not, and what to do when something goes wrong are described in [Migrating from the old 0.7 version](https://github.com/miyu-agent/miyu/blob/main/docs/en/guide/migrate.md).

The migration program first packs the whole old folder into an archive and verifies it file by file. It then reads only from the extracted copy, writes into the new version through the new core's protocol, and finally produces two reports: one for people to read, and one for an AI to read, which records where in the archive each item that was not migrated sits and what its old format looks like, so that you can have an AI continue the migration when you need to. The migration program does not modify the old folder. The archive and the reports go into `root/documents/旧版 Miyu 迁移/<time>/` in the new data root, so you can see them directly, uninstalling the package does not delete them, and they are backed up together with the data root.

The text printed in the terminal and the report for people are in Chinese or English, depending on the language. After connecting to the core, the migration program uses the language the core returns in the handshake (the interface language, or the system language); before connecting (for example, when showing help or reporting that it cannot reach the core), it uses the system language (`LC_ALL`, `LC_MESSAGES`, `LANG`): values starting with `zh` mean Chinese, and anything else means English. In English the folder is called `Old Miyu migration/`, and the two reports are called `report.md` and `for-agent.json`. The report for the AI has the same structure in both languages; the data migrated into the new version (sessions, memories, knowledge base names, the folders that hold files) does not change with the language.

The migration program connects to the new core as the user who runs it in the terminal (it reads `run/token` in the data root); if the core is not running, the migration program starts it with `miyu core`. Before it starts migrating, the migration program checks two things: first, whether the old version has stopped (`daemon.lock`); second, whether there is enough disk space. The disk that holds the archive needs free space of twice the size of the old folder, because the archive is counted as uncompressed and the extracted copy used for verification comes on top of it. The extracted copy lives in the migration package's state folder and is deleted once it has been used.

The following is migrated at present:

- **Personas**: the old Miyu becomes a new persona named Miyu. Its prompt is the original text from the old version (`crates/miyu-migrate/legacy/`), with the role-play prompt and example dialogue you changed laid over it; every persona you created yourself in `data/prompts/` becomes a corresponding new persona; developer mode maps to the shipped software engineer persona. If the new version already has a persona with the same name, the migration program does not create a new one and uses the existing persona instead. A persona's subsystems and plugin switches have no counterpart in the new version and are written into the report.
- **Sessions**: each session is exported as a read-only archive that you can browse and search but cannot continue; the text, the tool calls and their results, and the uploaded attachments are all kept. The summary lines are derived data and are not exported. Session ids are computed from the old ids, so running the migration again does not export anything twice.
  - QQ sessions are exported as archives of the group or private chat they belong to. Like the new version's QQ sessions, these archives do not appear in the session list, and the turn database records which group each one belongs to. In a group, each turn is split into what each person said, using the QQ number at the start of each line; in a private chat, a turn is what the other person said.
  - The turns that the old version moved out when it compacted a session (`evicted_context.db`) are put back into their original sessions by time; if the original session no longer exists, they go into a session named `旧版被挤出的对话` ("old conversation pushed out of context") for each persona.
  - Images produced by tools, images embedded for the model to see, and long output that overflowed are attached after the tool result they belong to; questions the AI asked you (`ask_user`), messages you inserted midway, and tool exchanges of which only the display transcript was kept are all preserved; a subagent's session becomes a child session and is exported together with its main session.

- **QQ message records**: the group and private messages recorded by the old version are converted into the format in which the chat platforms package stores messages (`qq-records.jsonl` in the folder of this run), and then handed to `miyu im records import` to be imported into the chat platforms database. The chat platforms package recognizes records that already exist (records from an earlier run, and the stretch that the new chat platforms package received in parallel), so nothing is imported twice. If the chat platforms package is not installed, the report states which command to run after you install it.

- **Memory**: the facts each old persona remembered are imported into the new persona it maps to, keeping the time each fact was recorded; facts about other people are filed under that person, and facts about you are filed under you. Facts the AI recorded about itself and facts longer than 120 characters are not imported, and the report states which line of the archive holds them. After the import, the migration program has the new version tidy the memory once, merging entries that duplicate existing memories. Running the migration again does not import anything twice, and facts you deleted are not brought back.

- **Settings and keys**: providers (address, key, the model's context window, temperature, price), the models for the main conversation and for reading images, the subagent pools, the search service's key, the "about you" section, and your QQ number are added to the new version's settings. The migration program only adds settings the new version does not have, and leaves settings that are already configured in the new version unchanged. Keys are written into the new version's secrets file, and the report only lists their names. Whole sections of settings that have no counterpart in the new version (context tuning, display, voice, ...) are written into the report. Provider ids are rewritten in the new version's form, and the report lists which ones changed; an id that contains Chinese gets a string computed from the old id appended to it, so running the migration again does not rename it, and two providers never end up with the same id.

- **Memes**: each meme library you collected yourself becomes a content package for the memes package, containing the images, their descriptions, when to use them, and where they were collected from. If the memes package is installed, the content package is installed directly; if it is not, the content package stays in the folder of this run, and the report states which command to run after you install it.

- **Skills and scripts**: the skills you wrote yourself are copied into the new version's skills folder. A skill whose name matches an existing skill does not overwrite it; it is copied under a new name and listed in the report. Links inside a skill are neither followed nor copied, and the report states how many there are; if a skill's `SKILL.md` is itself a link pointing outside the skill, the whole skill is not copied, and the report says so. Scripts you wrote yourself have a different format in the new version, so they stay unchanged in the archive and the report lists each of them; if the official package source already has a new package with the same name, the report suggests that you install it. Things installed by the old package manager are not copied, and the report states which new package to install from the official package source.

- **Knowledge base**: the documents you put into the old version are copied into a new knowledge base named `Old Miyu knowledge base` (`root/kb/legacy/`), and the new version builds the index itself; the old version's built-in default knowledge base is not migrated. If the old version's index file `kb_meta.db` is damaged or cannot be read, the report states the reason, and the documents stay in the archive.

- **Files**: the images, documents, tool outputs (sorted by session) and working folders that the old version kept for you are copied into the new version's pictures, documents and workspace folders; if the new version already has a file with the same name but different content, the migration program does not overwrite it, but copies the file under a new name and lists it in the report. Things the old version shared with other people are not migrated.

- **Login state of search scripts**: the Goofish login state is copied into the state folder of the new package `goofish` (provided that package is installed); searching Zhihu, Xiaohongshu and Bilibili has no package in the new version yet, so their login state stays in the archive; after you install the new Bilibili live-stream package, you need to log in again. The report only lists the sites and the number of entries, never the cookie contents.

- **Sponsorship records**: the sponsorship records are handed to the sponsorship plugin of the chat platforms package and imported into its ledger, keeping the original time, amount and exchange rate; the plugin recognizes records that already exist, so running the migration again does not import anything twice. If the plugin is not installed, the report tells you to run the migration again after installing it; if the plugin or Miyu is too old, the report states which one to upgrade before running it again. Foreign-currency amounts that the old version did not convert into yuan are recorded as "not converted", not as 0 yuan. If the session database is damaged or cannot be read, the report states the reason, and the records stay in the archive. The few records whose time cannot be parsed (a time without a time zone is parsed as UTC) are not migrated and stay in the archive, and the report states how many there are; all other records are imported normally.

- **What is not migrated**: usage, the input history recalled with the Up arrow key, QQ images, plugin data such as affection levels, memory diaries and old vectors, timed reminders and the like stay in the archive, and the report states for each item where it is and what format it has, so that you can have an AI continue the migration following `for-agent.json` (`给agent.json` in Chinese) when you need to. Derived caches are rebuilt by the new version itself. For things the old version installed outside the data root, the report only states whether they are still there: if `~/.local/bin/miyu` belongs to the new version (a link created by the install script that points into `~/.local/lib/miyu/`, or a wrapper script that mentions `miyu-remake`), the report says so and tells you not to delete it; the old fish configuration is looked up at `$XDG_CONFIG_HOME/fish/conf.d/miyu.fish`, or at `~/.config/fish/conf.d/miyu.fish` when that variable is not set; if it is a link to a place that no longer exists, the report lists it too, together with where it used to point. For the block that the old terminal integration wrote into bash and zsh startup files (`~/.bashrc`, `~/.bash_profile`, `~/.bash_login`, `~/.profile`, `~/.zshrc`, `$ZDOTDIR/.zshrc`), the report states the file and the line range; the migration program only reports it and does not modify it. When you run `miyu shellhook install` in the new version to install the integration for that shell, the new version first backs up the block and then removes it (the same goes for the fish file). The last section of the report says where the archive is and when you can delete the old folder (you do the deleting yourself).

The new core does not read a single byte of the old format: once all old users have migrated, this package will be withdrawn and the repository archived.

The next section is the maintainer's record of the steps on their own computer, not instructions for users.

## Running the migration on the project owner's real data root

The project owner's computer differs from the three commands above: the new version's data root is set by `MIYU_HOME` to `~/.cache/miyu-tui-home`, not `~/.miyu`, so the old folder `~/.miyu` does not need to be moved and can be handed to the migration program where it is. The commands below use fish, one code block per line, and you run them in order; you can stop and check after each step.

**0. Confirm two things first**

- The core needs to recognize "packages that only carry a subcommand" (the core side will give the minimum commit once its change is done); the deployed core is still the 11-03 build (`43ff9ee97`), so replace the core first.
- If you use the temporarily deployed wrapper script (`~/.local/bin/miyu`): it forwards by subcommand, so you need to add `migrate` to its list, or `miyu migrate` will open the terminal UI.

**1. Install the package** (pick one of two)

The first way is a local package file: a `.miyu` file built by CI, or one you built yourself by copying the program into `migrate/bin/` and the license into `migrate/LICENSE` in the repository and running `miyu pkg pack migrate --target linux-x86_64`; replace the path with the real one. The program asks once before installing; answer `Y`. Run:

```fish
miyu pkg install ./migrate-0.1.1-linux-x86_64.miyu
```

The second way is to wait until it is in the official package source and install it from there:

```fish
miyu pkg install migrate
```

After installing, confirm that `miyu migrate` is forwarded to the migration program (this command only prints the usage and changes nothing):

```fish
miyu migrate --help
```

**2. Stop the old core** (the one listening on port 8300; when to stop it is up to the project owner, and once it stops, the old version's QQ and web UI go offline)

First check whether it is running:

```fish
ss -ltnp | grep ':8300'
```

If it is running, stop it with the old version's own command. The `miyu` on this computer has already been replaced by the new version's wrapper script, and the old program is the renamed copy:

```fish
~/.local/bin/miyu.0.7.0-local.bak daemon stop
```

It does not matter if you have not stopped it: before it starts, the migration program tries to lock `~/.miyu/daemon.lock`, and if the old core still holds the lock, the migration program reports that the old version is still running and does not write a single byte.

**3. Back up the new data root** (for rolling back; first close the terminal UI, the web UI and the other interfaces that would start the core, and the new version's QQ will also go offline for a while)

```fish
miyu core stop
```

```fish
cp -a --reflink=auto ~/.cache/miyu-tui-home ~/.cache/miyu-tui-home.before-migrate
```

**4. Run the migration**

```fish
miyu migrate ~/.miyu
```

The migration program starts the core by itself. It first packs the whole of `~/.miyu` into an archive and verifies it file by file, then migrates from the extracted copy; `~/.miyu` itself is only read, never written.

**5. Read the reports**

When the migration finishes, it prints two paths. The reports are all in `root/documents/旧版 Miyu 迁移/` in the new data root, one folder per run, named after the time of that run (UTC):

```fish
ls ~/.cache/miyu-tui-home/root/documents/旧版\ Miyu\ 迁移/
```

Each folder contains `报告.md` (the report for people), `给agent.json` (the report an AI uses to continue the migration), `miyu-0.7.tar.zst` (the complete archive of the old folder) and `miyu-0.7.manifest.json` (the hash of every file in the archive); if the chat platforms package or the memes package is not installed, the folder also holds `qq-records.jsonl` and the memes content packages waiting to be imported.

```fish
less ~/.cache/miyu-tui-home/root/documents/旧版\ Miyu\ 迁移/*/报告.md
```

The archive is the only complete backup of the old folder. It lives in the data root, and `miyu pkg remove migrate` does not delete it; when you no longer need it, delete this folder yourself.

**6. Roll back when something goes wrong**

The old data root `~/.miyu` was never modified: whether the migration failed or you are unhappy with the result, the old version can still start normally. What needs undoing is what was imported into the new data root.

Undo everything (use this when you notice a problem right after migrating; anything you chatted or changed in the new version after the migration also goes back to the state before the migration):

```fish
miyu core stop
```

```fish
mv ~/.cache/miyu-tui-home ~/.cache/miyu-tui-home.after-migrate
```

```fish
mv ~/.cache/miyu-tui-home.before-migrate ~/.cache/miyu-tui-home
```

The reports of this run and the archive of the old folder are in `root/documents/旧版 Miyu 迁移/` inside `.after-migrate`; read them before you delete it.

Undo only part of it: for each category, the report states where it was written, how many entries were migrated and which ones were renamed. For the categories placed directly in the data root, deleting the corresponding folders undoes them:

- Skills: the skills under `root/skills/` that the report lists
- Knowledge base: `root/kb/legacy/` (the whole `Old Miyu knowledge base`)
- Files: the files the report lists in `root/pictures/` and `root/documents/`, plus `root/documents/旧版产物/` and `root/workspace/旧版/` (`root/documents/旧版 Miyu 迁移/` holds the archive and the reports, not migrated files; do not delete it along with them)
- Goofish login state: `root/state/scripts/goofish/goofish/legacy/`
- Memes: `miyu pkg remove legacy-memes-<library name>` (the report states which ones)

Personas, session archives, memories, settings and keys, QQ message records and sponsorship records are written into databases by the core and the chat platforms package, and there is no command to undo them entry by entry; to undo these categories, you can only use the full undo above.

## Development

During development, run these checks:

```
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

These are the same checks that CI (`.github/workflows/ci.yml`, on Linux, macOS and Windows) runs.
