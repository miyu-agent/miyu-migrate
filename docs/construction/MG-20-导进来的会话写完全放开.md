# MG-20 导进来的会话，权限级别写「完全放开」

核心施工 AUD-4 里和迁移程序有关的那一份（2026-11-13）。

## 为什么

- 核心 A16 起权限只剩「只读」「完全放开」两级（核心施工 LV-1）。以前的「工作区」`workspace` 核心一直照「完全放开」读，是为旧会话留的兼容。
- 项目主人 2026-11-13 定：还没发版，旧兼容的都去掉。核心 AUD-4 去掉读 `workspace` 的那一行：之后日志里记着 `workspace` 的会话，
  核心不认识这个级别，照只读算。
- 迁移程序拼 `session.created` 时写的一直是 `"permission": {"level": "workspace", "read_only": false}`（MG-3）。不改的话，核心改完以后
  用它导进来的会话全是只读的。

## 搜了什么

全仓库搜 `workspace`：当权限级别写的只有 `sessions/events.rs` 拼 `session.created` 的那一处。别的都是工作区目录（`root/workspace`）、
cargo 的 `--workspace`。

## 改了什么

1. `sessions/events.rs`：`level` 写 `full`。现在的核心读 `full` 和读 `workspace` 是同一个结果，所以这一版对没改的核心也成立。
2. `sessions/tests/turns.rs`：拼出来的 `session.created` 的 `permission` 是 `{"level": "full", "read_only": false}`。
3. 版本 0.1.3（`Cargo.toml`、`migrate/package.toml`、`Cargo.lock`），项目主人 2026-11-13 同意发。

## 不做什么

- 已经导进数据根的会话不改写：项目主人 2026-11-13 定旧会话直接删（核心 AUD-4 的施工单）。

## 怎么验

- 本机 `cargo fmt --all --check`；`cargo test`、`clippy` 在分支的三台 CI 上跑。
- 打 `v0.1.3` 以后看 Release 里三种系统的 `migrate-0.1.3-*.miyu`，软件源收进去。
